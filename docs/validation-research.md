# 参数校验设计调研手册

> 调研日期:2026-08-09 · 范围:Go 校验库 / 表达式引擎 / 标准库
> 目的:只取设计思想,代码全部自研。

## 1. go-playground/validator(事实标准)

**设计思想**

- **tag 驱动**:`validate:"required,min=3"` 声明式规则,字段就近可见;
- 规则预编译:struct 解析结果缓存,运行时零重复反射;
- 规则注册:`RegisterValidation(name, fn)` 自定义扩展;
- 嵌套遍历:`dive`(slice/map 元素)、嵌套 struct 自动递归;
- 跨字段:`eqfield` / `nefield`;
- 错误模型:ValidationErrors 聚合,含 Field / Tag / Param / Value。

**取其精华**:tag 驱动、规则预编译缓存、dive 嵌套语义、
自定义注册、聚合错误带字段路径。

**去其糟粕**:功能面大(数十种格式规则)、依赖多(crypto 等)、
默认值魔法多、错误翻译机制复杂;库体量与日常所需不成比例。

## 2. ozzo-validation

**设计思想**

- **可编程规则**:`validation.String.Required()` 链式构建,
  类型安全、IDE 友好;
- 规则组合清晰:`validation.Required.Or(validation.Empty)`。

**取其精华**:可编程组合的思想(可作自定义规则的辅助 API)。

**去其糟粕**:每个字段手写规则,结构体字段的声明式可读性差;
与 tag 生态不兼容。

## 3. protovalidate / CEL

**设计思想**:表达式引擎(CEL)驱动,支持复杂条件与跨字段逻辑。

**取其精华**:跨字段校验的表达式能力。

**去其糟粕**:引擎庞大、编译开销高、调试复杂;
99% 的日常校验是「必填 / 范围 / 格式 / 枚举」,用不上表达式。

## 4. go-validator(v2,已弃用)

**设计思想**:早期 tag 校验,规则简单。

**取其精华**:历史参照。

**去其糟粕**:停更多年,规则能力有限。

## 5. 标准库(net/mail、net/url、regexp、time)

**设计思想**:领域权威解析器内置(邮箱、URL、正则、时间)。

**取其精华**:格式校验直接复用标准库解析器,零第三方且语义权威。

**去其糟粕**:无声明式组合,需自建 tag 层。

## 6. 设计思想汇总

- tag 驱动声明式校验,字段就近可见;
- 规则预编译缓存,热路径零重复反射;
- 内置规则覆盖必填 / 范围 / 长度 / 格式 / 枚举;
- 格式规则复用标准库解析器(email→net/mail、url→net/url、
  ip→net.ParseIP、regexp→regexp 预编译);
- 嵌套结构体自动递归,slice/map 元素用 dive;
- 聚合错误带字段路径与规则名;
- 自定义规则实例级注册,无全局状态;
- 与 errx 打通:配置错误与校验失败统一错误模型。

## 7. 明确不采纳

- validator 的大而全规则面与翻译框架;
- CEL 表达式引擎;
- ozzo 的纯可编程 API(保留 tag 为主,可编程仅作补充);
- 全局注册表(实例级注册,测试与多租户安全)。

> 本手册为 validx 设计输入,不构成对外承诺;实现时按需取舍。
